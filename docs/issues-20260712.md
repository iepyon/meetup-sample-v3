- 階層はチケット登録時に **ラベル** で表現する
- ラベル設計:
  - 階層: `context:<bc>` / `feature:<flow>`
  - 種別: `type:scenario` / `type:policy`

- **実装済み範囲**:
  - community BC: `CreateCommunity` / `JoinCommunity` / `ApproveMember` / `RejectMember` / `LeaveCommunity`

- **未実装範囲**: `PublishEvent` 以降の event 全シナリオと POLICY、participation / checkin / notification BC 全体
- 参考実装は `snapshot/2026-04-19` ブランチ参照。以前存在した `status:refactor` item（notification BC の 4 通知 UseCase 抽出）は、抽出元の inline 実装自体が未実装に戻ったため `status:todo` に統一

## 凡例

各 item は以下のテンプレートで記述する。

```markdown
#### [item] <日本語タイトル>
- **Labels**: `context:<bc>` `feature:<flow>` `type:<scenario|policy>` `status:<done|todo>`
- **Who**: <アクター>
- **What**: <何を行うか>
- **Why**: <ビジネス価値・ハッピーパス上の位置付け>
- **受け入れ基準**:
  - [x/ ] 条件 1（done は `[x]`、todo は `[ ]`）
- **DML**: SCENARIO / POLICY 名、関連 EVT / CMD / QRY
- **関連コード** or **参考実装 (snapshot/2026-04-19)**: 実装ファイルパス
```

### Feature: コミュニティ管理

#### [item] 主催者がコミュニティを作成する
- **Labels**: `context:community` `feature:community-admin` `type:scenario` `status:done`
- **Who**: 主催者（Organizer）
- **What**: 名前・説明・カテゴリ・公開設定を指定してコミュニティを作成する。作成者を OWNER として同時登録する。
- **Why**: 主催者がイベント開催の母体となるコミュニティを立ち上げる起点となる。
- **受け入れ基準**:
  - [x] 名前が 1〜100 文字で指定できる
  - [x] 説明は 1000 文字以内・nullable である
  - [x] カテゴリは `TECH` / `BUSINESS` / `HOBBY` のいずれかである
  - [x] 公開設定は `PUBLIC` / `PRIVATE` のいずれかである

  - [x] 作成者が OWNER ロール・ACTIVE ステータスの `CommunityMember` として同時に作成される
  - [x] `CommunityCreated` が発火される
- **DML**: SCENARIO `主催者がコミュニティを作成する`, CMD `CreateCommunity`, EVT `CommunityCreated`

- **Labels**: `context:community` `feature:membership` `type:scenario` `status:done`

- **What**: 対象コミュニティへの加入を申し込む。公開設定に応じて即 ACTIVE / PENDING を分岐する。

#### [item] 定員を確定者数未満に減らせないようにする（D3）
- **Labels**: `context:event` `feature:event-planning` `type:scenario` `status:todo`
- **Who**: 主催者（Organizer）
- **What**: イベント編集時、新しい定員が現在の参加確定者数（APPROVED）を下回る場合に更新を拒否する。
- **Why**: 確定済みの参加者を勝手に外さない運用が前提。定員が確定者数を下回る「超過状態」は満席判定（`GetRemainingCapacity`）を狂わせ、キャンセル発生時の自動繰り上げが超過をさらに膨らませる構造的欠陥になる（T8・D3）。
- **受け入れ基準**:
  - [ ] `UpdateEvent` で `newCapacity < approvedCount` の場合 `CapacityBelowApprovedCountError` を返す
  - [ ] `newCapacity >= approvedCount` の場合は従来どおり更新が成功する
  - [ ] 確定者が 0 名のイベントでは 1〜1000 の範囲内で自由に定員変更できる
- **DML**: SCENARIO `主催者がイベントを編集する`（rule: capacity must not be reduced below current approved count）, CMD `UpdateEvent`, ERR `CapacityBelowApprovedCountError`, DECISION `D3`
- **依存**: 参加確定者数の取得を要するため **participation BC（`ApproveParticipations` / 参加集約）の実装後に着手可能**。参加機能が無い現状では判定材料が存在しない
- **参考実装**: なし（**snapshot/2026-04-19 にも存在しない新ルール**。D3 の決定と A2 のバックログ化に基づく新規実装）

## Context: participation

### Feature: 参加申込

#### [item] 参加者が参加申し込みをする
- **Labels**: `context:participation` `feature:application` `type:scenario` `status:todo`
- **Who**: 参加者（Member）
- **What**: 公開中イベントへの参加を申し込む。定員に空きがあれば APPLIED、満席なら WAITLISTED を同一トランザクションで分岐する。
- **Why**: 定員超過時もキャンセル待ちで拾える UX を提供し、主催者の後処理を自動化する。

### オープンクエスチョン（未決・次回セッションで決定）

- **Q4**: イベント中止後の参加レコードの後始末（`Participation` を一括取消するか・キャンセル待ち列をクリアするか）。一括取消は `ParticipationCancelled` 連発→繰り上げ暴発の連鎖リスクがあり、ガード設計とセットで要検討
- **Q5**: 一括承認で承認されなかった申込（否認・保留）の扱い。否認イベント・通知が未定義で、承認されない申込者は APPLIED のまま宙に浮く
