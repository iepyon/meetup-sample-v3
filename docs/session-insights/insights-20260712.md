**Q1. 今日「コミュニティ作成上限 10」のルールは usecase のカウントチェックのみで DB 制約がないと判明しました。この構成で上限が破れうる典型的な状況はどれですか？**

A) SQLite が COUNT クエリをサポートしないため常に破れる
B) 同一ユーザーの並行リクエストが両方ともチェック通過後に INSERT する（check-then-act の競合）
C) Prisma が unique 制約を SQLite に変換できないため
D) JWT の有効期限が切れたとき

<details><summary>答え</summary>

**B) check-then-act の競合**

「カウントを読む → 上限未満なら INSERT」という 2 ステップの間に他のリクエストが割り込めるため、アプリ層チェックだけでは同時実行で上限を超えうる（TOCTOU / check-then-act 競合）。メール一意性のように DB unique 制約があるルールは、最後の砦として DB が守る。集約カウント上限のような制約は unique では表現できないため、厳密に守るならトランザクション分離やロックが必要になる。

</details>

**Q2. この Wiki の各ページはフロントマターに `verified: <commit-sha>` を持ちます。この SHA の役割は何ですか？**

A) ページを書いた LLM のモデルバージョンを記録する
B) ページ内容を最後にコードと突合した時点の HEAD。`git diff <verified>..HEAD -- <sources>` で陳腐化を検出する
C) ページの改ざん検知用ハッシュ
D) コミット時に CI が自動採番するリビジョン番号

<details><summary>答え</summary>

**B) 陳腐化検出の基準点**

`sources`（根拠コードパス）と組み合わせ、「verified 時点以降に根拠コードへ差分があるか」を git で機械判定できる。差分があるページだけを `/wiki ingest` で見直せばよく、Wiki 全体の再検証を避けられる。これが Karpathy の LLM Wiki パターンにおける「安く鮮度を保つ」仕掛けの中核。

</details>

**Q3. glossary に「紛らわしい用語の弁別」欄を追加した動機は、`Event` 集約と「ドメインイベント」の衝突でした。DDD で「同じ語が文脈によって別の意味を持つ」問題への正攻法はどれですか？**

A) 全プロジェクトで用語を一意にするグローバル辞書を強制する
B) bounded context ごとにユビキタス言語を定義し、境界を越えるときは翻訳（context map）する
C) 曖昧な用語は英語ではなく日本語で書く
D) 意味が多い用語は使用禁止にする

<details><summary>答え</summary>

**B) bounded context ごとのユビキタス言語**

DDD では「語の意味は文脈（bounded context）内でのみ一意」であればよく、全体で一意にする必要はない。境界を越える連携では対応関係を context map として明示する。EventStorming ではこの「同じ言葉の意味が変わるサイン」が BC 境界発見の手がかりになる（本プロジェクトの DML では `LANGUAGE` として記録する）。

</details>

**Q4. domain-events.md には「7 つのイベントは publish されるが購読者はゼロ」と明記されています。In-Memory Event Bus で購読者を実装してクロスコンテキスト連携を始めた場合、同期呼び出しと比べた本質的なトレードオフはどれですか？**

A) イベント経由は常に高速になる
B) 発行側は誰が処理するかを知らず疎結合になるが、処理の完了保証・順序・失敗時の扱いが難しくなる（結果整合性）
C) イベント経由にすると型安全性が失われる
D) In-Memory ではプロセスを跨げないので意味がない

<details><summary>答え</summary>

**B) 疎結合と引き換えの結果整合性**

イベント駆動は「community が event コンテキストを知らない」疎結合を実現するが、副作用がいつ・確実に起きるかの保証は弱くなる（in-memory ならプロセス落ちで消失、リトライも自前）。だからこそ Wiki には「発火ポイントと将来の拡張点であり、実装済みの副作用ではない」と実装状況を区別して書いた。同一トランザクションで済む分岐は DML でも POLICY にせず SCENARIO 内の WHEN として書く、という今日のスキルのルールと同じ判断軸。

</details>

**Q5. Prisma で複合ユニーク制約（例: 同じユーザーは同じコミュニティに 1 回しか参加できない）を schema に定義する記法はどれですか？**

A) `@unique([communityId, accountId])` をフィールド行に付ける
B) モデルブロック末尾に `@@unique([communityId, accountId])` を書く
C) `@@index([communityId, accountId], unique: true)`
D) migration SQL に手書きするしかない

<details><summary>答え</summary>

**B) `@@unique([communityId, accountId])`**

単一フィールドは `@unique`（`@` 1 つ、フィールド行）、複合はモデルレベル属性 `@@unique`（`@` 2 つ、ブロック末尾）。本プロジェクトの CommunityMember がまさにこれで、「重複参加禁止」を usecase チェックと DB の二重で守っている。なお Prisma 6.x では `prisma/schema/` フォルダにモデルを複数ファイル分割する multi-file schema が GA（今日 `cat *.prisma` がサブフォルダを拾えず一瞬迷子になった構成）。

</details>
